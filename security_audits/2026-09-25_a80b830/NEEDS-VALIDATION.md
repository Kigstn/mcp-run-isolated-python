# Needs validation

These are prioritised leads with no severity. They are not confirmed vulnerabilities. Do not test them against live systems.

## TOCTOU in _remove_run_dir: a surviving sandbox descendant can make the unsandboxed server chmod any same-uid file or directory outside the run dir to 0700 (macOS CLI/library mode)

`code_executor._remove_run_dir/toctou-symlink-following-chmod-escapes-sandbox`

_remove_run_dir (code_executor.py:59-71) runs in the trusted server process, outside the srt sandbox, from the finally block of run_python_code. It does a top-down os.walk over the run directory. For each name in `dirs` it checks `is_symlink()` (an lstat, line 66) and then calls path-based `Path.chmod(stat.S_IRWXU)` (line 68). Path.chmod follows symlinks. The run directory is the sandbox's writable cwd (Popen cwd=code_path at line 141; allowWrite ['.'] in default_srt_settings.json line 10). So a sandbox process that is still alive during cleanup can swap a real subdirectory entry for a symlink between the check and the chmod, and the server then applies mode 0700 to the symlink's target outside the run dir. The target can be a directory or a regular file: os.walk classifies the entry when it scans the directory, and the swap happens after that, so the chmod lands on whatever the link points to. The sandbox cannot chmod outside its write scope itself, so this is a confused-deputy escape from the sandbox's write confinement, limited to setting mode exactly 0700 on objects the server uid owns. Verifier results: (1) Running the real, unmodified _remove_run_dir against a concurrent racer process in the parent sandbox, with 1 CPU, the race was won almost at once. A dummy directory outside the run dir went 0o555 -> 0o700 after 28 cleanup iterations (agents/ver-macrace/artifacts/evidence1.txt). A dummy regular file went 0o444 -> 0o700 after 9 iterations (agents/ver-macrace/artifacts/evidence3.txt). The hunter's third decisive fact (the window is winnable) is therefore settled locally, and the hunter's claim of 'directories only' is wrong. (2) In the Linux/Docker deployment (real srt+bwrap, user=nonroot, server root), a double-forked, setsid'd descendant did not survive a normal run exit (none alive afterwards; agents/ver-macrace/artifacts/evidence2.txt). The Linux/Docker path therefore has no racer, and the issue is limited to macOS (Seatbelt, no pid namespace, user=None). The root cause is distinct from u14. Descendant survival is only the prerequisite, and a setsid'd descendant leaves the process group, so even an os.killpg(proc.pid) on normal exit would not remove it. The sink here is the check-then-path-chmod pair. This fingerprint overlaps with the rmtree fingerprint only in that both fixes touch the same walk. The fix here specifically needs a no-follow, fd-relative chmod.

**Claimed root cause:** code_executor.py:66-68 checks is_symlink() (lstat by path) and then calls Path.chmod(stat.S_IRWXU) by path, which follows symlinks (os.chmod with follow_symlinks=True). The two are separate path-resolving syscalls on a sandbox-writable directory tree, and nothing does an O_NOFOLLOW/dir_fd-relative open or an fstat identity check between them. A sandbox descendant that is still running during cleanup can put a symlink into the window, and the unsandboxed server's chmod then goes to an arbitrary same-uid path.

3. **propagation** `src/mcp_run_isolated_python/code_executor.py:267` `CodeExecutor.run_python_code (finally)` — The finally block calls _remove_run_dir(code_path) in the trusted server process, outside the sandbox.
4. **propagation** `src/mcp_run_isolated_python/code_executor.py:66` `_remove_run_dir os.walk loop` — For a subdirectory name listed by os.walk, (Path(root)/name).is_symlink() does an lstat and returns False for a real directory. The descendant then replaces the entry with a symlink of the same name pointing outside the run dir.
5. **sink** `src/mcp_run_isolated_python/code_executor.py:68` `_remove_run_dir os.walk loop` — sub.chmod(stat.S_IRWXU) resolves the new symlink by path and sets mode 0700 on the out-of-tree target (directory or regular file) with the server's uid, outside sandbox write confinement.

Evidence:
- `src/mcp_run_isolated_python/code_executor.py:66` — The is_symlink() guard is an lstat by path, separate from the chmod that follows. This is the check side of the check/use pair.
- `src/mcp_run_isolated_python/code_executor.py:68` — Path.chmod(stat.S_IRWXU) is called without follow_symlinks=False and resolves by path. The real function, raced by a concurrent entry-swapper, changed an out-of-run-dir dummy directory 0o555 -> 0o700 in 28 iterations (agents/ver-macrace/artifacts/evidence1.txt) and a dummy regular file 0o444 -> 0o700 in 9 iterations (agents/ver-macrace/artifacts/evidence3.txt).
- `src/mcp_run_isolated_python/code_executor.py:165` — os.killpg(proc.pid, SIGKILL) runs only on timeout and only covers proc's process group. On normal exit nothing kills sandbox descendants. On Linux/Docker the bwrap pid namespace killed a setsid'd descendant anyway (agents/ver-macrace/artifacts/evidence2.txt: none alive), so only macOS is exposed.
- `src/mcp_run_isolated_python/code_executor.py:141` — Popen cwd=code_path (and CLAUDE_CODE_TMPDIR=code_path at line 147): the walked tree is the sandbox's working directory.
- `default_srt_settings.json:10` — filesystem.allowWrite ['.'] lets the sandbox create, rename and symlink entries inside the run dir, which is the tree _remove_run_dir walks.
- `src/mcp_run_isolated_python/code_executor.py:247` — The unshare wrapper applies only when sys.platform == 'linux'. On macOS there is no pid-namespace containment of descendants.

### Blockers
- macOS Seatbelt cannot run in the Linux parent sandbox, and running target code on the host macOS is prohibited. The end-to-end chain on the only affected platform cannot be observed here.
- Decisive fact 1 (owned by u14): on macOS with srt's Seatbelt backend and user=None, a setsid/double-forked descendant of the sandboxed interpreter keeps running after a normal (non-timeout) run exit and is still running while _remove_run_dir executes. This was refuted for Linux/Docker (evidence2) but is unverified on macOS.
- Decisive fact 2: srt's macOS Seatbelt profile lets that descendant rmdir/rename a subdirectory of its cwd and create a symlink there whose target is outside the allowWrite scope. Symlink creation is expected to be checked against the link path, not the target, but this is not verified.

### Local plan
On a macOS host with srt <=0.0.64 installed, create a scratch dir S containing S/work and a dummy S/dummy_target set to mode 0o555. Instantiate CodeSandbox/CodeExecutor with CodeSandboxSettings(user=None, code_timeout_seconds=10, path_to_srt_settings=<repo>/default_srt_settings.json, working_directory=S/work). Submit code that double-forks a setsid child and then exits normally. The child loops for about 10 s over os.mkdir('x'); os.rmdir('x'); os.symlink('S/dummy_target','x'); os.unlink('x'), ignoring OSError, in its cwd (the run dir). Call run_python_code up to about 50 times. After each call, stat S/dummy_target, and stop at the first mode change to 0o700. Also record whether the child is still alive (pgrep) right after the call returns, and whether os.symlink succeeded inside the sandbox. Use only dummy paths, and kill leftover children afterwards.

No real user directories or data, and no production host.

## On macOS (Seatbelt backend), processes started by sandboxed code outlive the run: nothing kills them on normal exit, a setsid() child escapes the timeout killpg, and survivors that keep stdio pin reader threads and pipe fds in the server

`code_executor._run_sandboxed:sandbox-descendants-outlive-run-without-pid-namespace`

At a80b830, CodeExecutor._run_sandboxed starts srt with start_new_session=True. It sends os.killpg(proc.pid, SIGKILL) only in the TimeoutExpired branch (code_executor.py:161-166), and the comment there relies on bwrap --die-with-parent. The interpreter command gets the unshare prefix only when sys.platform == 'linux' (code_executor.py:245-249). That prefix creates IPC and user namespaces, not a PID namespace. So on darwin the only containment for descendants is membership in the process group. From source, on the macOS backend (srt 0.0.64 sandbox-exec with process-fork and process-exec allowed, no PID namespace, and srt's cli.js calls process.exit when its direct child exits, with no tree kill): (a) when a run exits normally, a background child is never signalled, proc.wait returns, the run dir is removed and the tool returns; (b) on timeout, a descendant that called setsid()/setpgid() is outside the killed group. The survivor keeps running under the Seatbelt profile, as the server uid (in host CLI mode user defaults to None, so that is the invoking user), with no deadline. If it keeps the inherited stdout/stderr write ends, _drain blocks in read(65536) forever. reader.join(timeout=5) then gives up, the call is delayed about 10 s, buffered stdout is dropped, and 2 daemon threads and 2 pipe fds stay in the server for each such run. This is a possible path to fd exhaustion when the server's RLIMIT_NOFILE is low (macOS commonly defaults the soft limit to 256; not verified for deployments). Each detached process needs one request from any MCP client that can reach the server, or from a prompt-injected LLM. The per-run 'ulimit -u 256' added in a80b830 is not a lifecycle control. RLIMIT_NPROC is checked against the uid's total process count at fork time. It blocks the fork only when the server uid already has 256 or more processes (the dev host uid has 433) and never applies to uid 0. A dedicated service account with fewer processes can still fork. The executor-side lifecycle was reproduced with a stub srt that has no Seatbelt (agents/h-macos/artifacts/evidence1.txt): normal exit left a survivor, 10.3 s delay, output '', threads 1->3, fds 4->6; a timeout with a setsid child left a survivor; the control with no setsid was killed. Linux and Docker are not affected: at current source with real srt+bwrap (user=nonroot), neither the normal-exit+setsid child nor the timeout+setsid child survived, and threads and fds returned to baseline (agents/ver-macdetach/artifacts/evidence1.txt).

**Claimed root cause:** code_executor._run_sandboxed contains the sandbox's process tree only with a process-group SIGKILL on the timeout path. For everything else it relies on bwrap's PID namespace and --die-with-parent, which exist only on Linux. On normal exit there is no group or session kill, nothing tracks descendants that leave the group, and the drain pipes are never closed after reader.join times out. srt's macOS backend (sandbox-exec) provides neither a PID namespace nor a tree kill, and the a80b830 'ulimit -u' is a per-uid fork quota, not a lifetime bound.

### Trace and evidence

1. **entrypoint** `src/mcp_run_isolated_python/direct_use.py:60` `_CodeSandboxSyncClient.eval` — Caller-supplied Python code is passed to CodeExecutor.run_python_code. The unauthenticated MCP tool run_python_code (mcp_server.py) reaches the same executor.
2. **propagation** `src/mcp_run_isolated_python/code_executor.py:247` `CodeExecutor.run_python_code` — The unshare prefix is added only when sys.platform == 'linux', and it adds no PID namespace anyway. On darwin cmd is 'ulimit -u 256 ...; ulimit -f ...; exec "<python>" "<code.py>"'.
3. **propagation** `src/mcp_run_isolated_python/code_executor.py:149` `CodeExecutor._run_sandboxed` — start_new_session=True puts srt in a new session and process group. This is the only descendant containment the executor adds.
4. **propagation** `src/mcp_run_isolated_python/code_executor.py:160` `CodeExecutor._run_sandboxed` — proc.wait returns when srt exits, and srt exits when its direct child exits. Nothing is killed on the normal-exit path.
5. **propagation** `src/mcp_run_isolated_python/code_executor.py:165` `CodeExecutor._run_sandboxed` — On timeout only, os.killpg(proc.pid, SIGKILL) reaches members of the original group. It misses a descendant that has called setsid()/setpgid().
6. **propagation** `src/mcp_run_isolated_python/code_executor.py:168` `CodeExecutor._run_sandboxed` — reader.join(timeout=5) gives up while a survivor holds the inherited pipe write ends. The daemon threads and the proc.stdout/proc.stderr fds are never closed.
7. **sink** `src/mcp_run_isolated_python/code_executor.py:267` `CodeExecutor.run_python_code finally` — The run dir is removed and the call returns while the detached sandboxed processes keep running as the server uid with no deadline.

Evidence:
- `src/mcp_run_isolated_python/code_executor.py:161` — killpg exists only in the TimeoutExpired handler (161-166). The normal-exit path does no group or session cleanup.
- `src/mcp_run_isolated_python/code_executor.py:163` — The comment shows the design relies on bwrap --die-with-parent, which is Linux only.
- `src/mcp_run_isolated_python/code_executor.py:50` — _drain blocks in stream.read(65536) until EOF, which never arrives while a descendant holds the pipe.
- `src/mcp_run_isolated_python/code_executor.py:243` — 'ulimit -u 256' is RLIMIT_NPROC. It is counted per uid, only fails a fork when the uid already has 256 or more processes (not enforced for uid 0), and does not bound process lifetime.
- `tests/unit/code_executor/test_security.py:56` — test_timeout_kills_all_sandboxed_processes (49-64) covers only a same-pgid child on the timeout path, not setsid() or normal exit.
- `README.md:38` — Claims 'own pid namespace', which holds only for the Linux bwrap backend.
- `src/mcp_run_isolated_python/cli.py:37` — user defaults to None (passed through at 143), so in host CLI mode survivors run as the invoking user.

### Blockers
- Real macOS Seatbelt behaviour was not observed. sandbox-exec cannot run in the approved Linux container sandbox, and target or srt code must not run on the macOS host. From source, srt 0.0.64 macos-sandbox-utils.js:284-287 allows process-fork and process-exec, and cli.js:202-230 spawns with stdio 'inherit' and exits on direct-child exit with no descendant cleanup. However, survival past srt exit and killpg was shown only with a stub srt that has no Seatbelt (agents/h-macos/artifacts/evidence1.txt). The Linux control at current source left no survivors (agents/ver-macdetach/artifacts/evidence1.txt).
- Deployment-dependent and not established: whether any supported deployment runs the server or CodeSandbox directly on macOS, and whether the server uid has fewer than 256 processes and is not root. On the dev host the uid has 433 processes, so the a80b830 'ulimit -u 256' makes fork() fail with EAGAIN inside the sandbox and blocks the escape there.
- Not established: the RLIMIT_NOFILE of deployed macOS server processes, which decides whether the leaked pipe fds (2 per detached run) can reach EMFILE.

### Local plan
On a disposable macOS machine with srt 0.0.64, run as a dedicated non-root user with fewer than 256 processes (check with 'ps -U <user> | wc -l'). Use CodeExecutor(settings=CodeSandboxSettings(code_timeout_seconds=2, user=None, working_directory=<empty dir>, path_to_srt_settings=default_srt_settings.json, path_to_python_interpreter=<venv python>)). Case 1 (normal exit): code 'import os\nif os.fork()==0:\n  os.setsid(); os.execv("/bin/sleep",["sleep","4241"])\nprint("x")'. Case 2 (timeout): the same with tag 4242 plus 'import time; time.sleep(60)' in the parent. After each call returns, record the elapsed time, the output, 'pgrep -f "sleep 424[12]"', threading.active_count() and 'lsof -p <server pid> | wc -l'. Case 3: repeat case 1 with os.close(1); os.close(2) in the child to separate survival from the fd leak. The finding is confirmed if any sleeper survives. The fd/thread part is confirmed if fds and threads grow by 2 per run in cases 1 and 2. Run cases 1 and 2 once more as a desktop user with 256 or more processes to record whether fork fails with EAGAIN. Kill all sleepers afterwards. Fix: always os.killpg the group after proc.wait(). On backends without PID isolation (non-Linux), either refuse to run or supervise and kill the full descendant tree (for example, track the session and the processes of the sandbox uid). Close proc.stdout/proc.stderr after the joins. Add tests for the setsid and normal-exit variants.
